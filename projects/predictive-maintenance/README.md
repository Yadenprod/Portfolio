## 📋 Описание проекта

Система прогнозного обслуживания оборудования для промышленных предприятий. Позволяет мониторить состояние оборудования в реальном времени, анализировать данные с датчиков, генерировать прогнозные оповещения и планировать обслуживание для минимизации простоев и предотвращения дорогостоящих поломок.

## 🏗️ Архитектура

### Технологический стек

- **Backend:** Laravel (PHP), RESTful API, Eloquent ORM

### 6. **Dashboard и аналитика**
- Сводка ключевых метрик (оборудование, датчики, оповещения)

## 🎯 Архитектурные решения и обоснование

### 1. **RESTful API архитектура**

**Проблема:** Нужна четкая структура взаимодействия между frontend и backend, поддержка разных клиентов (веб, мобильное приложение)

**Решение:** RESTful API с ресурсными контроллерами (`Route::resource()`), стандартизированные HTTP методы (GET, POST, PUT, DELETE)

**Почему так:**
- Стандартизация упрощает разработку и поддержку
- Легко добавлять новые клиенты без изменения backend
- Кэширование на уровне HTTP (GET запросы)
- Масштабируемость через горизонтальное масштабирование API серверов

**Реализация:**
- 8 ресурсных контроллеров (Equipment, Sensor, SensorReading, MaintenanceLog, Alert, Dashboard, Auth)
- Стандартизированные ответы JSON
- Пагинация для больших списков (`per_page`, `page`)

### 2. **Eloquent ORM с Relationships**

**Проблема:** Прямые SQL запросы усложняют поддержку, изменение схемы БД требует изменения кода

**Решение:** Eloquent ORM с relationships (`hasMany`, `belongsTo`)

**Почему так:**
- Автоматическая загрузка связанных данных через `with()`
- Защита от N+1 проблемы (eager loading)
- Легко менять БД без изменения кода (SQLite → MySQL)
- Валидация данных на уровне модели

**Реализация:**
- Equipment → hasMany(Sensor), hasMany(MaintenanceLog), hasMany(Alert)
- Sensor → belongsTo(Equipment), hasMany(SensorReading)
- SensorReading → belongsTo(Sensor)
- Alert → belongsTo(Equipment), belongsTo(Sensor)

### 3. **Vue.js SPA с Vue Router**

**Проблема:** Многостраничное приложение требует перезагрузки страниц, медленный UX

**Решение:** Single Page Application (SPA) с Vue Router для навигации без перезагрузки

**Почему так:**
- Быстрая навигация между страницами (< 100ms)
- Переиспользование компонентов
- Защищенные маршруты (требуют авторизации)
- Сохранение состояния при навигации

**Реализация:**
- 12 Vue компонентов (views)
- Vue Router с защищенными маршрутами
- Axios для HTTP запросов к API
- LocalStorage для хранения токена авторизации

### 4. **Chart.js для визуализации данных**

**Проблема:** Текстовые данные с датчиков сложно анализировать, нужна визуализация трендов

**Решение:** Chart.js с vue-chartjs для интерактивных графиков

**Почему так:**
- Интерактивные графики (zoom, pan, tooltips)
- Разные типы графиков (line, bar, scatter)
- Адаптивный дизайн
- Легко добавлять новые типы графиков

**Реализация:**
- Графики исторических показаний датчиков
- Фильтрация по датам
- Экспорт данных в CSV

### 5. **Docker для изоляции и масштабирования**

**Проблема:** Разные окружения (разработка, production), сложная настройка зависимостей

**Решение:** Docker Compose с отдельными контейнерами для backend, frontend, MySQL, Nginx

**Почему так:**
- Изоляция окружений, одинаковое поведение на всех машинах
- Легкое масштабирование (можно запустить несколько экземпляров)
- Простое развертывание (одна команда `docker-compose up`)
- Отдельные контейнеры для каждого сервиса (микросервисная архитектура)

**Реализация:**
- Backend контейнер (Laravel + PHP)
- MySQL контейнер для БД
- Nginx контейнер для статики и проксирования
- Volumes для персистентности данных

### 6. **Пагинация с гибкими параметрами**

**Проблема:** Большие списки (тысячи записей) замедляют загрузку и отображение

**Решение:** Пагинация с параметрами `page` и `per_page`, поддержка `per_page=-1` для получения всех записей

**Почему так:**
- Быстрая загрузка страниц (10-50 записей вместо тысяч)
- Гибкость: можно получить все записи для экспорта
- Стандартизированный формат ответа (Laravel pagination)
- Метаданные (total, last_page, prev_page_url, next_page_url)

**Реализация:**
- `EquipmentController::index()` с пагинацией
- Поддержка `per_page=-1` для экспорта CSV
- Метаданные для навигации по страницам

### 7. **Фильтрация и поиск на уровне API**

**Проблема:** Клиент должен фильтровать данные на frontend, что неэффективно для больших объемов

**Решение:** Фильтрация и поиск на уровне API через query параметры

**Почему так:**
- Фильтрация на уровне БД быстрее (индексы, оптимизированные запросы)
- Меньше данных передается по сети
- Можно комбинировать фильтры (status + search)
- Поддержка сложных запросов (LIKE, WHERE, OR)

**Реализация:**
- `EquipmentController::index()` с фильтрами: `equipment_id`, `search`, `status`
- Поиск по нескольким полям (name, type, location)
- Приоритет фильтров (equipment_id > search)

### 8. **Factory Pattern для тестовых данных**

**Проблема:** Нужны тестовые данные для разработки и демонстрации, ручное создание неэффективно

**Решение:** Laravel Factories с Faker для генерации реалистичных данных

**Почему так:**
- Быстрая генерация больших объемов данных
- Реалистичные данные (русские названия, даты, значения)
- Легко менять структуру данных
- Можно использовать в тестах

**Реализация:**
- 6 фабрик (Equipment, Sensor, SensorReading, Alert, MaintenanceLog, User)
- Seeders для заполнения БД
- Русские названия и описания

### 9. **CORS конфигурация для безопасности**

**Проблема:** Frontend и backend на разных доменах, нужна защита от CSRF атак

**Решение:** CORS конфигурация с белым списком разрешенных доменов

**Почему так:**
- Защита от несанкционированных запросов
- Поддержка production домена (dma-tech.ru) и localhost для разработки
- Настройка credentials для передачи cookies/tokens

**Реализация:**
- `config/cors.php` с `allowed_origins: ['https://dma-tech.ru', 'http://localhost:3000']`
- Поддержка credentials для авторизации

### 10. **Модель Alert с автоматической генерацией**

**Проблема:** Нужно автоматически генерировать оповещения при выходе показаний за нормы

**Решение:** Модель Alert с полями severity, type, message, resolved_at

**Почему так:**
- Централизованное управление оповещениями
- Отслеживание разрешенных/неразрешенных оповещений
- Классификация по степени серьезности
- Связь с оборудованием и датчиками для контекста

**Реализация:**
- `Alert` модель с relationships
- Dashboard показывает неразрешенные оповещения
- Фильтрация по severity (Критическая, Высокая, Средняя, Низкая)

## 📊 Структура данных

### Equipment (Оборудование)
- `id`, `name`, `type`, `location`, `installation_date`, `status`
- Relationships: sensors, maintenanceLogs, alerts

### Sensor (Датчик)
- `id`, `equipment_id`, `name`, `type`, `unit`, `min_threshold`, `max_threshold`, `status`
- Relationships: equipment, sensorReadings

### SensorReading (Показание датчика)
- `id`, `sensor_id`, `value`, `reading_time`
- Relationships: sensor

### Alert (Оповещение)
- `id`, `equipment_id`, `sensor_id`, `type`, `message`, `severity`, `alert_time`, `resolved_at`
- Relationships: equipment, sensor

### MaintenanceLog (Журнал обслуживания)
- `id`, `equipment_id`, `description`, `maintenance_date`, `status`
- Relationships: equipment

## 🚀 Установка и запуск

### Требования
- Docker и Docker Compose
- Git

### Запуск через Docker

```bash
# Клонирование репозитория
git clone <repository-url>
cd yasfags

# Запуск всех сервисов
docker-compose up -d --build

# Инициализация БД (в контейнере backend)
docker-compose exec app php artisan migrate
docker-compose exec app php artisan db:seed
```

- Frontend: `http://localhost:8080`
- Backend API: `http://localhost:8000`
- Nginx: `http://localhost:80`
