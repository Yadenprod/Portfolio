### 💹 [Gaming Stock Market](projects/gaming-stock-market/) - **Real-Time Trading Platform**
![Status](https://img.shields.io/badge/Status-Production-green) ![Complexity](https://img.shields.io/badge/Complexity-⭐⭐⭐⭐⭐-orange) ![Stack](https://img.shields.io/badge/Stack-ASP.NET%20Core%20%7C%20React-blue)

Полнофункциональная биржа акций для игровых персонажей с real-time торговлей, построенная на микросервисной архитектуре.

**Технологический стек:**
- **Backend:** ASP.NET Core 8.0, PostgreSQL (Entity Framework Core), SignalR Hubs (TradingHub, NotificationHub), JWT Authentication, Serilog
- **Frontend:** React 18.2, TypeScript, Redux Toolkit (5 slices: auth, trading, player, notification, achievement), React Router, Vite, Tailwind CSS, Chart.js, socket.io-client для SignalR
- **Интеграции:** Stripe API (StripeWebhookController), Real-time через SignalR Hubs
- **Архитектура:** Repository Pattern (11 репозиториев: IUserRepository, IPlayerRepository, ITeamRepository, IOrderRepository, ITradeRepository, IUserPortfolioRepository, IMatchRepository, IPriceHistoryRepository, ITransactionRepository, IAchievementRepository, INotificationRepository, IAuditLogRepository), Event-driven (OnTradeExecuted), Background Services (5 hosted services: PriceUpdateService, DataParsingService, MarketMakerService, NotificationService, AuditService)

**Ключевые особенности:**
- ⚡ **Real-time торговля** через SignalR Hubs с задержкой < 50ms
- 📊 **In-memory OrderBook** (`SortedDictionary`) для мгновенного матчинга ордеров с Price-Time Priority алгоритмом
- 🏆 **Система достижений** с интеграцией в TradingService
- 💳 **Интеграция платежных систем** (Stripe API через PaymentService)
- 🔒 **Безопасность:** Rate limiting (10 запросов/10 секунд), JWT tokens, 2FA, KYC, Audit Logging
- 📈 **Аналитика:** Real-time графики через PriceChart/VolumeChart, история сделок, портфолио трекинг
- 🎯 **Динамическое ценообразование:** 6-факторная модель (PriceCalculator) с защитой от манипуляций
- 👥 **Система уровней:** 4 уровня пользователей (Novice, Trader, Expert, Master) с комиссиями 0.5%-2%

**Метрики производительности:**
- ⚡ Задержка матчинга ордеров: < 50ms через in-memory OrderBook
- 📊 Backend: 11 сервисов (IUserService, IJwtService, IPaymentService, IAnalyticsService, IAchievementService, IDataParser, IPriceCalculator, ITradingService, IEmailService, IKycService, ITwoFactorAuthService, INotificationService), 10 контроллеров (TradingController, PlayersController, AuthController, PortfolioController, PaymentController, AchievementsController, NotificationController, AdminController, AnalyticsController, StripeWebhookController), 11 репозиториев, 5 Background Services (PriceUpdateService, DataParsingService, MarketMakerService, NotificationService, AuditService), 2 SignalR Hubs (TradingHub, NotificationHub)
- 📱 Frontend: 20+ страниц (HomePage, LoginPage, RegisterPage, DashboardPage, PlayersPage, PlayerDetailsPage, TeamsPage, TeamDetailsPage, PortfolioPage, OrderBookPage, TradeHistoryPage, SettingsPage, NotificationsPage, AchievementsPage, AdminDashboard, UserManagement, PlayerManagement, TeamManagement, OrderManagement, TransactionManagement, AnalyticsDashboard), 5 Redux slices (auth, trading, player, notification, achievement), Chart.js для графиков, socket.io-client для подключения к SignalR
- 💾 In-memory OrderBook: SortedDictionary с кастомным компаратором (descending для buy, ascending для sell), Price-Time Priority алгоритм
- 🔄 Real-time обновления: SignalR Hubs (TradingHub, NotificationHub), socket.io-client на frontend
- 📈 Rate Limiting: 10 запросов/10 секунд через FixedWindowLimiter

**Архитектурные решения и обоснование:**

1. **In-memory OrderBook (`OrderBook.cs`):**
   - **Проблема:** Торговля требует задержки < 50ms, а запросы к БД дают 10-100ms
   - **Решение:** `SortedDictionary<decimal, List<Order>>` для buy/sell ордеров с кастомным компаратором
   - **Почему так:** O(log n) поиск лучшей цены, O(1) добавление ордера, матчинг за микросекунды
   - **Компромисс:** БД используется только для персистентности после исполнения сделки через событие `OnTradeExecuted`

2. **6-факторная модель ценообразования (`PriceCalculator.cs`):**
   - **Проблема:** Простая формула не учитывает волатильность рынка, манипуляции
   - **Решение:** Модель с 6 факторами: производительность (40%), турниры (30%), популярность (20%), команда (10%), объем торговли (динамический), волатильность (динамический)
   - **Почему так:** Каждый фактор взвешен по важности, динамические факторы адаптируются к рынку
   - **Защита:** Лимит изменения цены в день (100%) предотвращает резкие скачки

3. **SignalR для real-time:**
   - **Проблема:** HTTP polling дает задержку 1-5 секунд, не подходит для торговли
   - **Решение:** SignalR WebSocket с автоматическим fallback на long polling
   - **Почему так:** Задержка < 50ms, автоматическое переподключение, масштабирование через backplane

4. **Repository Pattern:**
   - **Проблема:** Прямые запросы к БД усложняют поддержку и смену БД
   - **Решение:** Интерфейсы `IOrderRepository`, `IUserRepository`, `IPlayerRepository` и т.д.
   - **Почему так:** Изоляция бизнес-логики от БД, можно менять БД без изменения логики, упрощение поддержки

5. **Event-driven архитектура:**
   - **Проблема:** Прямые вызовы между сервисами создают жесткие зависимости
   - **Решение:** События `OnTradeExecuted` для уведомления других сервисов
   - **Почему так:** Слабая связанность, легко добавлять новые обработчики (аналитика, уведомления, достижения)

   - **Решение:** TypeScript типы для параметров навигации (brand, model)

- 📊 **Статистика:** Отслеживание производительности каждого метода (method_performance), общая статистика (total_solved, success_rate, avg_confidence)

Проекты для изучения технологий и экспериментов с автоматизацией:

### 🚤 [GTA Boat Bot](projects/gta-boat-bot/) - **Computer Vision Automation**
Автоматизированный бот для управления лодкой в GTA с детекцией целей на миникарте.

**Технологический стек:**
- **Language:** Python
- **Computer Vision:** OpenCV, HSV color detection
- **Architecture:** State Machine, Object Detection
- **System:** Windows API (SendInput для клавиатуры), MSS для захвата экрана

**Архитектурные решения и обоснование:**

1. **State Machine паттерн (`state_machine.py`):**
   - **Проблема:** Бот должен собирать чекпоинты в определенной последовательности. If-else цепочки были бы нечитаемыми (3984 строки кода)
   - **Решение:** State Machine класс с явными переходами между состояниями (`SIMPLE_TRANSITIONS` словарь)
   - **Почему так:** Переходы явные и понятные, легко добавлять новые состояния, логика изолирована от детекции
   - **Результат:** Читаемый код, легко отлаживать, легко расширять

2. **HSV color detection с кэшированием (`detector.py`):**
   - **Проблема:** Детекция цветов на миникарте должна быть быстрой (90+ FPS), но `cv2.inRange` медленный при частых вызовах
   - **Решение:** HSV кэширование, предобработка изображения один раз, затем быстрый поиск контуров через `cv2.findContours`
   - **Почему так:** HSV более устойчив к освещению чем RGB, кэширование снижает нагрузку, контуры дают точные координаты
   - **Результат:** Детекция 8 цветов за < 11ms

3. **Low-level keyboard control через SendInput:**
   - **Проблема:** `pynput` медленный и ненадежный для игр, может быть заблокирован античитом
   - **Решение:** Windows API `SendInput` через ctypes для прямого управления клавиатурой
   - **Почему так:** Низкоуровневый контроль, быстрая отправка команд, меньше вероятность обнаружения

**Метрики производительности:**
- ⚡ Детекция цветов: < 11ms для 8 цветов
- 🎯 FPS обработки: 90+ FPS
- 🏗️ State Machine: Упрощение логики с 3984 строк до читаемой структуры
